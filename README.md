# 团队报名候补引擎

进程内 TypeScript 库：多个活动赛道共享的确定性候补（waitlist）引擎。
无界面、无鉴权、无持久化；调用串行执行。

## 使用

```ts
import { WaitlistEngine } from "./src/engine";

const engine = new WaitlistEngine(
  [{ id: "A", capacity: 4 }, { id: "B", capacity: 1 }],
  [["A", "B"]],            // 对称冲突；同赛道恒与自身冲突；冲突不传递
);
const id = engine.register("A", ["m1", "m2"]); // 返回严格递增的报名标识
engine.withdraw(id);                            // 撤回候补或已录取报名
const view = engine.inspect();                  // 只读快照，不改变状态
```

构建与测试（仅需 Node.js）：

```sh
npm install
npm test
```

## 设计说明

### 确定性递补如何维持

每次 `register` / `withdraw` 完成自身状态变更后，引擎执行递补循环：
反复取出“当前可整体录取且创建序号最小”的候补并录取，直到不存在可录取候补。
关键观察：**录取只会消耗容量与成员资格，绝不会让原本不可录取的候补变为可录取**。
因此候补从“不可录取”变为“可能可录取”只有三类触发事件：

1. 新增候补（它自己）；
2. 撤回已录取报名使某赛道剩余容量增大；
3. 撤回已录取报名使某些成员的占用赛道集合缩小。

引擎为这三类事件各维护一个索引，递补循环只消费索引推出的候选：

- **就绪堆**：按创建序号排序的最小堆，存放“可能可录取”的候补。它只是提示结构，
  弹出时完整复检（容量 + 每位成员的冲突位图）；失效或暂不可录取的条目被惰性丢弃
  并重新归类。堆顶即全局序号最小者，保证选择顺序与全量扫描规则完全一致。
- **容量索引**：未因成员冲突阻塞的候补，按赛道 + 团队人数（1..20，仅 20 个桶）分桶。
  赛道剩余容量从 f1 增至 f2 时，只有人数落在 (f1, f2] 的候补可能新变为容量可行，
  只访问这些桶；人数 ≤ f1 的候补此前已是容量可行（若在等待必因成员冲突，容量变化
  与之无关），人数 > f2 的仍然不可行。
- **成员阻塞索引**：因成员冲突阻塞的候补，按其每个成员反查。仅当某成员的占用状态
  变化（撤回已录取报名）时，才访问该成员关联的候补并复检；与其无关的候补（哪怕
  有 10 万条）完全不被触碰。

冲突判定用 64 位位图：每条赛道一个冲突位掩码（含自身位），每位成员维护其已录取
赛道集合的位图，一次按位与即可判定，与赛道数无关。

### 操作成本

设候补团队人数为 k（≤20），一次撤回释放的成员关联的阻塞候补数为 w，容量窗口
(f1, f2] 内命中的候补数为 c，一次操作中实际被录取的报名数为 a：

- `register`：O(k) 归类 + 递补循环；
- `withdraw`（已录取）：O(k + w + c) 触发工作 + 递补循环；
- `withdraw`（候补）：O(k) 从索引摘除，不触发递补；
- 递补循环：每条被录取的报名 O(k) 录取 + O(log n) 堆操作；每条被复检但暂不可
  录取的候选 O(k)，且这类复检必由上述真实状态变化引起，总量正比于受影响候补数；
- `inspect`：O(报名总数 + 赛道数)，只读。

即：一次局部操作的成本正比于**受影响（被访问）的候补数量**，与候补总量无关。
规模测试（`test/scale.test.ts`）构造 10 万条因成员永不释放而不可录取的候补，
再执行 2000 次局部撤回/新增：诊断计数器显示整个过程中仅 2000 条候补被访问、
2001 次可录取性复检（每次操作约 1 条），证明不存在全量扫描。

### 不变量

- 团队只整体录取，占用名额等于成员数，赛道占用永不超容量；
- 同一成员所有已录取报名所在赛道两两不冲突（含同赛道）；
- 候补不占名额、不占成员资格；已撤回报名不参与递补；已录取报名不被挤出。

## 测试

- `test/engine.test.ts`：确定性场景（队首大团队不阻塞小团队、跨赛道撤回后
  早序号候补先录取并反向阻断、第三赛道照常递补、序号单调、非法输入）。
- `test/random.test.ts`：30 个种子 × 120 步随机操作，与测试内独立的全量扫描
  参考模型（`test/reference.ts`）逐步比对全部报名状态与各赛道占用；覆盖非传递
  冲突、多人重叠、撤回候补与撤回已录取报名。
- `test/scale.test.ts`：10 万候补规模测试，用 `engine.stats` 诊断计数证明
  局部操作不扫描无关条目。
